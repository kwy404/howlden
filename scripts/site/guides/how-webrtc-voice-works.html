The short version: from your mouth to their ears

When you talk in a browser voice channel, a long chain of work happens in a fraction of a second. Your browser captures the microphone, compresses the sound with Opus, wraps each slice in an encrypted packet and sends it along the best path it found. The listener's browser reorders the packets, patches over missing ones, decodes them and plays them.

All of that is WebRTC, a set of standards and browser APIs from the W3C and the IETF. Every modern browser ships it, which is why howlden can offer voice chat with nothing to install. Below, each link of the chain comes with a short snippet you can paste into your browser console. For the big picture of direct connections, read peer to peer chat explained.

Step 1: capturing the microphone

Everything starts with navigator.mediaDevices.getUserMedia(). The browser asks the person for permission, and only pages served over HTTPS (or from localhost) are allowed to ask at all. If the person agrees, the page receives a MediaStream with one audio track.

const stream = await navigator.mediaDevices.getUserMedia({
  audio: {
    echoCancellation: true,
    noiseSuppression: true,
    autoGainControl: true
  },
  video: false
});
const [mic] = stream.getAudioTracks();
console.log(mic.label, mic.getSettings());

Those three options matter. Echo cancellation stops other people's voices from looping from your speakers back into your mic. Noise suppression tones down fans and keyboards, and automatic gain control evens out your volume. Browsers usually enable them for calls anyway. The track is also a live handle: setting mic.enabled = false sends silence without tearing anything down, one simple way to build a mute button.

Step 2: the offer, the answer and the missing piece called signaling

The microphone track is handed to an RTCPeerConnection. Before two browsers can talk, they must agree on codecs, encryption and which network addresses might work. One side writes those details into an offer, and the other replies with an answer. Both are plain text in a format called SDP (Session Description Protocol).

const pc = new RTCPeerConnection({
  iceServers: [{ urls: "stun:stun.l.google.com:19302" }]
});
stream.getTracks().forEach((track) => pc.addTrack(track, stream));
pc.ontrack = (event) => {
  const audio = new Audio();
  audio.srcObject = event.streams[0];
  audio.play();
};
pc.onicegatheringstatechange = () => {
  if (pc.iceGatheringState === "complete") console.log(pc.localDescription.sdp);
};
await pc.setLocalDescription(await pc.createOffer());

WebRTC deliberately does not say how the offer and answer travel between browsers. That job, called signaling, is left to the app, and most apps run a signaling server for it. howlden has no server, so people carry the messages: the offer is compressed into an invite link or QR code you send through any messenger, and the friend's browser answers with a short reply code that comes back the same way. Waiting for candidate gathering to complete, as the snippet does, puts every address into one description, so one round trip is enough.

Step 3: ICE finds a path through the network

Most devices sit behind a router doing NAT (network address translation), so their own address is not the one the internet sees. ICE (Interactive Connectivity Establishment, described in RFC 8445) solves this by collecting candidates:

  • Host candidates: the local addresses of your device, useful when both people are on the same network.
  • Server reflexive candidates: your public address as seen from outside, learned by asking a STUN server. howlden uses Google's free public STUN servers for this, and they never see your calls.
  • Relay candidates: an address on a TURN server that forwards packets, available only if you configured one.

ICE then pairs up both sides' candidates and runs connectivity checks, small probes sent from both ends at about the same time, so each router sees outgoing traffic first and lets the reply in. The best working pair wins, and ICE keeps checking in the background. When every pair fails, usually because both people are on strict networks such as some corporate, school or mobile carrier connections, you get "connection failed". The guide on strict NAT and TURN servers covers what to do then.

Step 4: DTLS and SRTP lock the connection

Encryption in WebRTC is not optional. As soon as ICE has a working path, the two browsers run a DTLS handshake over it (DTLS is TLS adapted for UDP). Each browser uses a certificate it generated itself, and the SDP it sent earlier contains a fingerprint of that certificate in a line starting with a=fingerprint. The handshake fails if the certificate on the wire does not match the fingerprint in the description, so the connection is exactly as trustworthy as the path that carried the offer and answer.

The handshake then produces keys for SRTP (Secure Real time Transport Protocol), which encrypts every audio and video packet. Text messages and files use data channels, which run over SCTP inside the same DTLS session. This is end to end encryption between the two browsers, and no setting can turn it off.

What stops someone from swapping the invite link for their own and sitting in the middle? That is why howlden shows a short connection fingerprint both people can compare, ideally aloud on the call. If they match, nobody replaced the keys. A den passphrase adds a second AES-GCM layer, with a key derived through PBKDF2, on top of messages and files. None of this protects a device that is already compromised.

Step 5: Opus, packets and the jitter buffer

Browsers must support Opus (RFC 6716), a codec built for this job. In calls it typically uses 20 millisecond frames at a 48 kHz clock and lowers its bitrate when the network gets worse. Its forward error correction can tuck a low quality copy of earlier audio into the next packet, so one lost packet does not leave a hole.

Packets travel over UDP, which never waits for retransmissions, because a word that arrives half a second late is useless in conversation. The receiving browser keeps a small jitter buffer that holds packets just long enough to reorder them and play them at an even pace, growing when the network is shaky. When a packet is truly lost, packet loss concealment fills the gap with a plausible guess, which is why bad calls sound robotic rather than silent. You can watch this live with getStats():

const report = await pc.getStats();
report.forEach((s) => {
  if (s.type === "codec") console.log("codec", s.mimeType, s.clockRate);
  if (s.type === "inbound-rtp" && s.kind === "audio") {
    console.log("lost", s.packetsLost, "jitter", s.jitter);
  }
  if (s.type === "candidate-pair" && s.nominated) {
    console.log("round trip", s.currentRoundTripTime);
  }
});

In Chrome, the page chrome://webrtc-internals draws the same numbers as graphs for every open connection, and Firefox has about:webrtc.

From two people to a whole den

Everything above describes one connection. A howlden den is a full mesh: every member has its own peer connection, ICE path and DTLS keys with every other member. After the first invite round trip, howlden introduces the new member to the rest of the den over the encrypted connections that already exist.

The trade off is upload: your browser sends a copy of your voice to each person, so with eight people you upload seven streams. Opus voice is light, so audio holds up well, but video is much heavier, which is the main reason a den is capped at 8 people. Server based tools instead use a media server that receives one stream from you and forwards it to everyone, which scales to large meetings. The mesh keeps traffic between the people in the room, and the server approach handles crowds.

One more honest limit: with nothing in the middle, everyone has to be online at the same time.

See it for yourself

Open a den in one browser, invite yourself from a second browser or your phone, join the voice channel, and keep chrome://webrtc-internals open in another tab. You will see the candidates, the chosen pair, the Opus codec and the jitter buffer at work. For the API reference, the MDN WebRTC documentation is a good next stop, and if you would rather just talk, the guide to voice chat in the browser with no download shows the everyday side. When you are ready, start a den and say hello.
